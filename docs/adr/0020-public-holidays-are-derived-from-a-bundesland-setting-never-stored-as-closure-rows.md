# Public holidays are derived from a Bundesland setting, never stored as closure rows

A public holiday is "a special type of closure" (issue #167's own words): on a public holiday
the childcare day disappears exactly as it does for a plain `Closure` (since ADR-0021 a closure may instead keep the day — a public holiday never does) (CONTEXT.md) — no pickup
is needed, because the facility is shut *and* both parents are off work. Today a parent has to
notice every German public holiday themselves and type it in one at a time through the closure
range form, which is both tedious and a correctness risk — a missed Reformationstag looks like an
uncontested childcare day until someone is surprised by a closed door.

## Decision

**A household picks its state (`Bundesland`) once; that state's public holidays are computed at
read time and merged into the closure list the calendar, pickup-request generation, and the
at-risk cron all already read — never written as rows.**

`src/domain/services/publicHolidays.ts` holds a hand-rolled table of the 16 German states' public
holidays (nine nationwide plus each state's own subset — Heilige Drei Könige, Fronleichnam, and
so on), keyed off an Easter-Sunday calculation (the anonymous Gregorian algorithm) for the
movable feasts. `publicHolidayClosures({ state, pattern, from, to })` turns a state + window into
`Closure` values with `kind: "public-holiday"`, filtered to the weekdays the household's
*effective-dated* pattern (ADR-0002) actually includes on each date — so a holiday that lands on
a weekend, or on a weekday a household never has childcare on, correctly produces nothing at all,
not a closure that overrides "hide weekend days" (#130). `mergeClosures(stored, derived)` unions
the two per date, stored always winning: a parent's own manual closure on a holiday date keeps its
own reason and stays editable, the derived one is simply dropped for that date.

Only **state-wide, unambiguous** holidays are derived. A handful of German holidays are scoped to
individual municipalities rather than a whole state — Mariä Himmelfahrt in Bayern (observed only
in majority-Catholic municipalities, unlike Saarland where it is state-wide), Fronleichnam in parts
of Sachsen and Thüringen, the Augsburger Friedensfest (Augsburg alone) — and those are left out.
A *spurious* derived holiday hides a day that genuinely needs a pickup, which is the dangerous
direction for an app whose whole job is surfacing exactly that; a *missing* one costs a parent one
manual closure, the same cost every closure already has today. Conservative inclusion is the only
defensible default.

`households.bundesland` (migration `0012`) is a nullable `text` column with a check constraint on
the 16 ISO 3166-2:DE codes — no default, so an existing household (or a fresh seed) keeps today's
behaviour exactly: `NULL` means no derived holidays at all, the same as if #167 had never shipped.
Changing it goes out under the existing catalogue event 11 `childcare-pattern-changed`
(`src/app/settings/childcareActions.ts`'s `setBundeslandAction`), not a new event — it changes
which days are childcare days precisely the way a pattern edit does, same recipient, no reason to
grow the catalogue past 12 events for what is the same kind of change.

## Alternatives considered

**Materialise a row per derived holiday, generated by a job.** Would need a generation job to run
on some horizon, a job to re-run when the Bundesland changes (re-deriving potentially years of
history), and a decision about how far ahead to pre-generate — three new moving parts for a fact
that is already a pure function of `(date, state)`. Rejected: everything the app already treats as
derived rather than stored (the childcare day itself, ADR-0002; Day state, ADR-0003) follows the
same logic, and public holidays fit the pattern exactly — recompute is free, and changing the
Bundesland takes effect instantly with nothing to backfill or invalidate.

**An npm holiday-calendar package** (`date-holidays`, `feiertagejs`). Sixteen states and roughly a
dozen deterministic rules each is a small, finite, rarely-changing table — not worth a dependency,
and ADR-0005 keeps the domain framework-free with a deliberately lean dependency list. A
hand-rolled table is also the only way to apply this ADR's state-wide-only filter precisely,
rather than inheriting whatever municipality-level nuance (or lack of it) the package ships with.

**Deriving every known municipality-level holiday too**, with the household picking a city instead
of a state. Rejected for the same reason the exclusion list exists: a municipality-scoped holiday
is not simply "harder to look up" — it is genuinely ambiguous without knowing which municipality,
and getting it wrong hides a day that needs a pickup.

## Consequences

`Closure` gains an optional `kind: "manual" | "public-holiday"` (`src/domain/types.ts`) — absent
means manual, the same convention `reason` already follows — and `Household` gains an optional
`bundesland`. Both domain services that read closures today (`recordAbsence`,
`runAtRiskEscalation`) now also take a `HouseholdRepository` dependency to resolve the setting;
every production caller already builds their deps by spreading `...createRepositories(tx)`, which
already carries `households`, so no call site changed — only the test fakes did.

The UI gets one new primitive, `src/ui/Select` (RAC `Select`/`Popover`/`ListBox`, ADR-0011) — the
16-state picker is the first place a plain closed-set dropdown was needed; `ToggleGroup` (a
multi/single *key row*) is the wrong shape for 16 long state names. A derived holiday renders as
the *same* `closed` display state (`dayDisplayState()` is untouched — no new domain Day state, no
fifth `Legend` entry) but with a distinct badge glyph and tint (`DayCell`'s new `isHoliday`
modifier, orthogonal to `state` the same way `isToday` is) and its own copy ("Public holiday — no
childcare", `StatePill` reading "Holiday") so a parent can see *why* the day is closed without
opening it. The household settings tab gains a read-only list of the derived holidays, with no
Edit/Remove — `ClosureRepository.save`/`delete` remain stored-rows-only, so there is no code path
that could reach a derived closure to begin with.

School holidays (`Schulferien`), Kita closing periods, and any other recurring-but-not-public-
holiday closure are out of scope — not derivable from a Bundesland alone, and stay ordinary manual
closures.
